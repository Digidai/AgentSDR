本轮增加 **52 项审计测试**。把同一组测试放到修复前的 `fc015a9` 隔离副本运行，**28 项失败、24 项通过**；修复后 **52 项全部通过**。28 是失败场景数，部分场景有共同根因，不应解释为 28 个互不相关的漏洞。[基线结果](bug-audit-baseline.json)保留了完整场景名称。

完整 Cloudflare 原生测试共 **243 项通过**，TypeScript、前端及录音扩展构建通过，依赖审计 **0 个已知漏洞**。另有 **19 项编译后 workerd 检查通过**，包含实际队列消费、发送收据、重复消息去重、150 列配置和 R2 隔离。外部供应商传输在本地被替换为测试响应，没有发送真实邮件或发起真实电话。

本轮基于线上当时的 `e533184` 及其文档提交 `fc015a9`，保留了此前的连接修复。生产工作区已经初始化，未运行会创建或清理工作区的 fresh-install 检查。

## 高风险修复

| 问题 | 修复前的可复现场景 | 修复与验证 |
| --- | --- | --- |
| **跨工作区 R2 访问和删除** | 修改自己联系人 `custom.photo_key`，可读取另一个工作区的图片；删除自己的联系人还会删除该外部对象 | 图片路径必须属于当前工作区的图片命名空间；读取、替换、删除均检查。隔离副本证明原版读出 200、外部对象被删除；修复后 404，外部对象保留。编译后 Worker 也验证通过 |
| **收到回复后仍发送旧跟进** | 排队中的 CRM 草稿没有被作废，序列又清掉草稿关联，导致发送任务把它当普通草稿发出；暂停序列也漏掉取消 | 新回复同时作废 pending/queued 草稿并停止 active/paused 序列，保留历史关联；发送前用原子条件重新确认客户、草稿和序列状态 |
| **手动登记回复绕过取消逻辑** | 手动记录消息没有推进 CRM 上下文，也没有取消 CRM 跟进 | 所有入站消息使用同一接收流程，消息、去重、取消、上下文和 CRM 待办一起保存 |
| **发送状态保存不完整** | 审批和任务分开保存，中断会留下无人处理的 queued 草稿；发送成功后进度或事件保存失败会把成功收据改成 uncertain | 审批与任务一起保存；成功收据、草稿、序列进度、事件、任务完成一起提交；已进入发送边界的内容保存不可变快照 |
| **人工核对恢复了已经停止的触达** | 将 uncertain 核对为 sent，会把已回复的客户重新放回 active；两次核对还可提交相反结果 | 仅推进仍 active 且步骤一致的报名；核对使用原子状态条件，只允许一个结果成功；用冻结内容重建核对收据，保持回复后的停止状态 |
| **工作区可能没有任何 owner** | 两个并发降级请求都看到两个 owner，最后全部被降级 | 最后一个 owner 的约束放进同一条更新语句；成员删除也在实际删除时再次排除 owner |
| **AI 绕过人工审核** | 低置信度分类被策略保留审核，但任务尾部又直接把客户改为 interested | 阶段变化统一受分类策略控制；上下文与客户状态在提交时再次比较；新回复后的旧建议不能被直接采纳 |
| **不要联系只改变了呼叫列表** | 在列表标记 do_not_call，客户仍然可创建新呼叫和继续跟进 | 统一设置客户 DNC、停止触达、作废草稿并更新呼叫联系人；迟到的自动呼叫结果不能覆盖 DNC |

## 并发、恢复和计算修复

- 同一草稿的并发收据可能把 CRM 步骤推进两次；现在以草稿 ID、步骤和活动状态进行条件更新。
- AI 起草期间收到新回复，会产生失去有效序列的旧草稿；现在仅在上下文与序列仍有效时插入和关联。
- 暂停中的草稿生成任务曾被标记为完成，恢复后无法重试；现在延迟等待，并遵守下次跟进时间。
- Gmail Cron、推送和续页任务可能竞争同一邮箱的游标；现在用 D1 租约串行处理同一邮箱，逐页持久化，最终游标与续页状态一起提交。Cron 只对 Gmail 邮箱安排 Gmail 同步。
- 录音完成接口的并发提交会重复应用未接通计数；现在仅成功完成状态转换的一次请求应用结果。
- 公式的自身引用被过滤掉，循环未被识别；现在拒绝并返回可处理的 400。
- AI/集成的物理输出列缺少父列依赖，列重排后公式会先计算出错误的 0；现在加入父列依赖。
- 只运行末端列会跳过它依赖的计算列；现在补齐传递依赖。
- 修改公式或供应商配置仍使用旧成功缓存；现在使变更及其下游结果失效，推进行版本，取消旧任务并阻止旧结果覆盖。
- 停止表格只取消任务，行仍 queued，无法重新运行；现在重置行、取消运行记录并用行版本拦住迟到的 HTTP 结果。
- 大 LOOKUP 表一次性读入可能耗尽 Worker 内存；现在加载前检查总量，源数据总预算 1 MiB，展开后预算 2 MiB，超限返回明确错误。
- 表格变更分批处理 JSON 路径，保持在 [D1 的 SQL 参数和函数参数限制](https://developers.cloudflare.com/d1/platform/limits/)内；在真实编译后的 workerd 上验证 150 列。
- 长关键词或非英文搜索会遇到 D1 的 LIKE 模式字节限制；现在使用普通子串查询，关键词中的 `%`、`_` 按文字搜索。
- `phoneNumber` CSV 表头经过小写转换后未匹配别名，号码丢到 custom；现已修复。
- 页面切换时的数据 hook 曾保留上一个联系人的结果；现在按请求路径关联结果，切换目标后立即隐藏旧目标数据。本项经静态检查与构建验证，未声称完成浏览器交互验收。
- 密码重置先消耗令牌再保存密码，保存失败会烧掉令牌，旧的其他重置链接也仍有效；现在密码、会话撤销和全部旧重置令牌一起提交。
- 撤销较旧但同名阶段的分类会覆盖较新的历史；现在检查最新分类，并为撤销批次加唯一标记，防止并发覆盖。

## 验证边界和上线

本地全部使用临时 D1/R2、合成身份和供应商测试响应。额外的 19 个跨工作区资源读写用例均拒绝访问。现有 191 项测试也继续通过。

架构保持 Workers、D1、R2、Queues、Cron、Workers AI。本轮没有修改已应用的迁移或增加数据库迁移，Gmail 同步租约复用 D1 的内部 preferences。生产上线后的检查脚本只发 GET、不带登录态、不调用供应商、不修改业务数据。

上线状态以 [bug-audit-deployment.json](bug-audit-deployment.json) 和 [bug-audit-live-verification.json](bug-audit-live-verification.json) 为准。初始迁移和连接修复的旧证据继续保留。

本轮不是“永远没有 Bug”的证明。真实 Gmail/Resend 投递、LinkedIn/WhatsApp 权限、手机麦克风、Chrome 扩展交互及真实电话仍需要受控的真实账号验收；没有据自动测试宣称这些已经通过。按照仓库 AGENTS.md，本轮未运行未经请求的浏览器自动化。外部供应商已接受的请求无法撤回；结果不明确的发送仍保持待人工核对，避免自动重发。
